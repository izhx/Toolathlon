你负责分析并设计一组用于大规模 agent 训练数据合成的高保真 MCP 模拟环境。

仓库：
/data8/zhangxin/teleai/Toolathlon

分析对象：
google-cloud
google_calendar
google_forms
google_sheet
notion
snowflake
wandb
github
huggingface

一、核心目标

这些 mock 将用于后续大规模、多样化的 agent 数据合成。
未来任务可能显著超出当前 tasks/finalpool 的范围。

目标是尽可能保持真实 MCP 对 agent 呈现的接口、业务语义、
状态变化和交互规律，使合成轨迹能够训练可迁移到真实环境的能力。

当前任务仅用于：
- 提供真实使用案例
- 帮助发现隐藏依赖
- 作为部分回归验证样例

不得将“支持现有任务所需的最少接口”作为最终设计边界，
也不得围绕已有任务答案或固定调用顺序实现模拟逻辑。

允许评估代码实现、LLM 驱动仿真以及两者结合的混合实现。
根据行为保真、开发成本、运行成本、稳定性和可验证性选择方案，
不预设所有对象必须使用同一种技术。

本阶段只做可行性分析和设计：
允许编写分析文档和只读扫描脚本；
不实现 mock，不修改现有任务行为，不启动完整 benchmark，
不执行真实服务写入、资源清理或全局部署。

二、分析范围与保真原则

以可核实版本的 MCP 实际暴露能力作为第一层分析边界，
同时追踪支撑这些能力所必需的后端服务语义。

区分：
1. MCP 已暴露的能力。
2. 后端服务具有、但当前 MCP 未暴露的能力。
3. 初始化、SDK、CLI、评测等其他入口额外使用的能力。

不要默认需要复刻整个云平台。
如果某项后端能力并不影响目标接口及其合理使用，
可以不实现，但必须说明边界。

对于尚未覆盖的功能，应设计明确的失败或不支持行为，
不能返回伪造的成功结果。

目标运行环境优先采用本地或自控服务，
使业务状态、账号、数据和执行过程可管理、可重置、可复现。
模型 API（包括仿真 LLM）、安装依赖及其他公网需求单独记录。
本机、Docker 和内网访问不算公网访问。

三、先建立统一的保真标准

在深入分析各对象前，定义所有 mock 共用的保真维度。

至少包含：

1. 工具接口保真

核实并记录：
- 工具名称与说明
- 输入 schema、必填字段、默认值与校验规则
- 返回内容结构、内容类型与必要元数据
- 工具可见性和配置开关
- 错误的表示方式
- 适用时的资源、提示模板及协议行为

明确哪些差异会改变 agent 的工具选择和参数生成。

2. 业务语义保真

操作应满足真实服务的主要业务约束。
分析资源之间的关系、合法状态、状态转换与不变量。

例如：
创建对象后应能查询；
修改应影响后续读取；
删除应正确处理对象及其引用；
无效操作应产生合理错误。

不能只模拟响应格式而不实现对应语义。

3. 跨操作与跨入口一致性

同一资源经不同工具访问时应具有一致的身份和状态。
涉及 MCP、SDK、HTTP、CLI 等多个入口时，
分析它们是否需要共享同一份后端状态。

检查分页、搜索、过滤、排序、批量操作和直接读取之间的一致性。

4. 身份、权限与时间行为

按实际能力分析：
- 用户、组织、项目、工作区、角色和权限
- 无权限、不存在、冲突、重复请求等错误
- 时区、时间戳、版本、并发更新
- 异步任务、处理中间态、最终一致性和限流

不要假定所有行为都需要完整模拟。
根据对 agent 行为与数据质量的影响决定保真优先级。

5. 数据和环境分布

环境应能生成多样、合理、具有内部关联的数据，
而不只是反复使用一份固定 fixture。

分析资源数量、层级、内容长度、历史记录、缺失字段、
近似名称、重复内容、干扰项、权限差异等如何变化。

区分：
- 接口保真
- 业务状态保真
- 数据分布逼真
- 运行规模与性能

不要用一个笼统评分掩盖其中的明显短板。

四、统一源码与能力摸底

先阅读仓库适用的 AGENTS.md 和 docs/mcp-analysis.md。
已有文档只作为线索，配置和实现以当前源码为准。

检查：
- configs/mcp_servers/
- utils/mcp/tool_servers.py
- utils/roles/task_agent.py
- utils/app_specific/
- 与目标服务相关的 SDK、CLI 和直接 HTTP 调用
- 安装脚本、锁文件、可用的固定版本 MCP 源码
- tasks/finalpool 中的任务、初始化与评测代码
- 可用的现有调用轨迹

不要只依赖任务声明或现有轨迹统计能力。
已有轨迹只证明某些路径被使用过，不代表全部合法操作。

对于远程动态工具集合：
记录已核实的工具版本或快照及配置条件；
无法核实的部分标记待确认，不推断成确定能力。

需要查阅外部资料时，优先使用对应版本的源码和官方文档，
记录来源、版本与查阅日期。

不要执行可能触发业务初始化的配置导入。
不要在文档中保存凭据、Cookie 或 token。

五、每个对象必须完成的分析

1. 能力清单

列出工具或能力族，并标注：
- 来源与版本
- 读取、写入、执行或管理属性
- 操作对象
- 依赖的状态和约束
- 已有任务是否使用
- 对未来多样任务的适用价值
- 当前证据完整程度

同一能力族中的工具可以合并解释，
但工具清单应足以核对覆盖情况。

2. 领域状态模型

设计支撑合理工具组合的状态模型，包括：
- 实体、字段、关系
- ID 与 URL
- 版本和历史
- 约束与生命周期
- 身份与权限
- 文件、附件和二进制对象
- 适用时的异步任务与执行结果

说明哪些状态需要持久化，
哪些可以派生，以及不同入口如何访问同一状态。

3. 关键交互序列

设计超出当前任务的代表性交互序列，例如：
- 创建 → 查询 → 修改 → 再查询 → 删除
- 搜索 → 分页 → 定位对象 → 批量更新
- 遇到权限或参数错误 → 调整操作 → 成功
- 两个工具共同操作一个资源
- 跨服务传递资源或内容

覆盖合理的不同调用顺序，
不要把实现绑定到某条已知成功轨迹。

4. 候选实现方案

比较适用的方案：
- 保留真实 MCP server，替换其后端
- 有状态的 MCP 替代实现
- 本地 HTTP/API 替代服务
- SDK/client 适配
- 复用现有本地服务或模拟器
- 静态 fixture 或回放作为辅助
- LLM 驱动的仿真器
- LLM 与规则引擎、状态存储或真实执行组件组合的混合仿真器
- 上述方法的组合

说明各方案对接口保真、业务语义、实现成本、
可扩展性、性能和维护成本的影响。

给出首选方案与备选方案。
不要假定所有对象采用同一种技术。

如果建议使用现成模拟器或数据库，
核实实际覆盖范围和兼容缺口，
不能仅凭产品名称相似就认定可替代。

5. 保真缺口与取舍

按能力明确区分：
- 可依据源码或规范较准确复现
- 可实现语义近似，需要说明偏差
- 实现代价较高，建议分阶段支持
- 证据不足，需要进一步确认

说明每项偏差可能让 agent 学到什么错误规律，
以及如何验证或降低影响。

不要将“工具能调用”视为“已经高保真”。

6. LLM 仿真可行性

每个 MCP 报告必须回答：
- 哪些能力适合使用 LLM，哪些不适合？
- 建议采用代码、LLM 主导还是混合方案？
- LLM 可以决定哪些内容，哪些必须经过外部校验？
- 主要保真风险及验证方法是什么？
- 相较纯代码实现，开发成本与长期合成成本如何变化？

具体分析要求见第八节。

六、面向大规模数据合成的设计

分析环境如何支持以下需求：

1. 多样初始状态

支持按 seed 和配置生成环境，
变化资源规模、内容、关系、历史和权限等。

生成数据应满足业务约束，
既包含可完成任务的资源，也包含合理干扰信息。

2. 任务与环境的对应关系

说明如何：
- 从环境状态生成任务
- 或根据任务约束构建环境
- 验证任务可解
- 允许不同但正确的执行路径
- 避免资源名称和模板规律直接泄露答案

环境模拟器、任务生成器和评测器应有清晰职责。

3. 独立结果验证

设计基于状态、约束或业务结果的验证方法。
不要仅靠工具返回的 success 字段或 agent 自述判断成功。

避免模拟器与评测器复制同一段错误逻辑，
导致错误行为被共同接受。

不得将 groundtruth 暴露给 agent，
也不得按任务答案直接生成工具结果。

4. 并发、隔离和复现

分析：
- 大量 episode 的状态隔离
- 并发创建与更新
- seed、虚拟时间和随机性控制
- 快照、克隆、重置与回放
- 异常中断后的恢复
- 状态存储和吞吐瓶颈

区分复现能力与过度固定：
可复现不意味着所有任务使用相同数据和调用顺序。

5. 数据质量与迁移风险

识别可能产生低质量轨迹的因素，例如：
- 总是成功的写操作
- 缺少真实约束
- 过度简化的工具输出
- 无效但被接受的参数
- 过于规则的资源命名和数据模板
- 不符合真实服务的错误恢复方式
- 查询结果与实际状态不一致

为主要风险设计检测指标或验证方法。
评估组合操作和未见过的任务结构，
不能只回归当前 finalpool 的固定案例。

七、各服务的重点问题

1. Google 相关服务

分别分析 google-cloud、google_calendar、
google_forms、google_sheet。

检查认证、Drive、资源 ID、URL 和跨 API 访问的共享部分。
不因属于同一厂商就假设认证方式和状态模型相同。

2. google-cloud 与 snowflake

特别分析 SQL 方言、类型、NULL、时间、
对象存储、任务执行和服务特有约束。

不能默认换成本地 SQL 引擎即可达到兼容。
需要给出支持边界、语义差异和验证方法。

3. notion、github、huggingface

重点分析结构化资源、版本、文件、
身份权限以及多入口共享状态。

不能只替换 MCP 调用，却遗漏相关的 SDK、HTTP 或 CLI 路径。

4. wandb、huggingface

实际暴露能力可能与版本或配置有关。
必须基于可核实的工具集合设计。

当前任务只使用读取能力，
不能自动成为忽略已暴露写入能力的理由。

八、评估使用 LLM 作为仿真器

允许将 LLM 用于模拟工具行为、生成响应内容、解释复杂操作、
提出状态变化，以及构造多样化环境数据。

不要预先限定只能采用确定性代码实现。
对每个 MCP，评估以下路线的可行性：
- 主要由代码和规则实现
- 主要由 LLM 驱动仿真
- 由 LLM 与确定性组件共同实现

根据行为保真、实现成本、运行成本、稳定性和可验证性选择方案。

1. 明确 LLM 的职责

逐项判断哪些部分适合由 LLM 承担，例如：
- 生成符合业务背景的初始数据和非结构化内容
- 模拟难以完整实现的复杂接口行为
- 根据操作与当前状态提出状态变更
- 生成符合接口契约的自然语言或半结构化返回内容

同时判断哪些部分更适合使用确定性组件，例如：
- schema 校验
- 资源 ID 和引用关系管理
- 权限检查
- SQL 或代码的真实执行
- 精确计算、排序、分页
- 状态持久化与并发控制

不要仅因某个接口难实现，就默认交给 LLM；
说明这样做可能引入的语义偏差。

2. 显式管理环境状态

即使采用 LLM 主导的仿真，也应设计可检查、可持久化的环境状态，
不能仅靠模型对历史对话的记忆维持资源和业务关系。

重点评估以下结构：

工具调用 + 当前相关状态
→ LLM 提出响应和状态变更
→ 校验接口契约、权限及业务不变量
→ 原子提交状态变更
→ 根据已提交状态生成或核对最终返回

说明：
- 如何检索本次调用需要的状态，避免上下文遗漏
- 如何处理超出上下文容量的环境
- 如何避免响应与实际提交结果不一致
- 校验失败时如何修复、重试或返回错误
- 多次调用及并发调用如何保持一致

这是一种候选架构，可以提出其他结构，但必须解释其一致性保障。

3. 限制无依据的补全

读取已有资源时，返回值必须能够追溯到环境状态。
需要生成新内容时，应明确它属于初始化、合法创建操作，
还是服务本身允许的生成行为，并按需要写入状态。

不能因为 agent 希望某项操作成功，就：
- 自动补齐不存在的资源
- 忽略权限或业务约束
- 将非法参数解释成合法操作
- 编造执行结果
- 悄悄修复本应让 agent 处理的错误

4. 隔离仿真与任务求解

仿真 LLM 的职责是模拟环境行为。
不要向它提供不必要的任务答案、评分目标或成功轨迹，
也不要让它通过返回内容提示 agent 如何完成任务。

区分服务原本会提供的帮助信息与仿真器额外泄露的解题信息。
环境中的文本应作为业务数据处理，不能覆盖仿真器的行为规则。

5. 验证 LLM 仿真的质量

设计针对以下问题的验证：
- 同一状态下重复读取是否一致
- 写入后不同工具看到的结果是否一致
- 长交互序列是否出现状态漂移
- 是否接受真实接口应拒绝的操作
- 是否出现资源、字段或执行结果幻觉
- 是否过度倾向成功、简化任务或帮助 agent
- 新任务和未见调用组合下是否仍满足业务约束

不能仅使用同一个仿真 LLM 自评其正确性。
结合独立规则、状态检查、真实服务记录、
受控差分验证和必要的人工抽查。

6. 规模、成本与复现

估算每次工具调用引入的模型调用次数、上下文规模、
延迟、费用及并发需求，说明估算依据和不确定性。

分析是否可以通过以下方式降低成本：
- 确定性快速路径
- 按能力选择不同模型
- 缓存、批处理和状态摘要
- 提前生成环境内容
- 将已经稳定的行为逐步转为代码实现

记录模型版本、提示词版本、输入状态、模型输出、
校验结果及最终提交的状态变更。
不要仅凭固定采样参数宣称可复现，应设计可验证的回放机制。

7. 输出要求

将各 MCP 的 LLM 适用范围、职责边界、校验机制、
保真风险及成本比较写入对应服务报告。

总体报告比较不同路线，并推荐适合验证 LLM 仿真价值的试点。
不要求所有 MCP 使用 LLM，也不预设 LLM 方案一定优于代码实现。

九、共享知识与工作流

采用多 agent 协作完成本次分析。
由 1 个统筹 agent 负责全局协调，每轮建议并行运行最多 3 个领域 agent，
实际并发数不得超过运行环境的可用额度。
将 9 个 MCP 分配为独立分析任务，按批次完成；每个领域 agent 一次负责一个 MCP。
交叉审查安排在后续轮次，复用可用并发名额。

1. 模型要求

统筹、领域分析和交叉审查均使用当前环境可用、
适合复杂推理与代码分析的最强模型，不按角色分配轻量模型。
本次默认目标模型为 gpt-6-astra，推理强度为 xhigh。
如迁移到其他运行环境，应先核实模型可用性和能力，再确定统一目标模型。

统筹会话应在启动时选择目标模型；本 prompt 本身不能切换已经启动的会话模型。
创建子 agent 时显式指定同一模型和推理强度，
或在运行平台支持继承时确认其实际继承值。
记录各角色实际使用的模型及推理强度，不要只依据角色名称或默认值推断。

额度不足时优先降低并发、分批执行，不自行降低模型能力或推理强度。
若无法满足目标模型要求，应报告实际限制，不得静默降级。

上述模型要求用于执行本次设计分析的 agent。
待设计的 MCP 仿真器使用什么模型，仍应按保真、成本和验证结果单独评估。

2. 角色与文件职责

统筹 agent：
- 完成公共框架摸底，定义保真标准、公共术语和服务报告模板
- 分派任务，维护任务进度和共享知识
- 维护总体报告、共享文档、能力矩阵、合成设计和验证计划
- 复核公共发现，解决跨报告冲突，汇总架构和实施优先级

领域 agent：
- 先读取共享材料，再分析所负责 MCP 的源码和能力
- 比较代码实现、LLM 主导仿真和混合方案
- 只维护自己负责的服务报告
- 将公共发现、证据冲突和共享组件建议提交给统筹者复核合并

交叉审查 agent：
- 尽量由非原作者审查服务报告
- 检查证据、能力覆盖、状态一致性、保真缺口和验证方案
- 检查与其他服务报告及共享设计的冲突
- 提交具体问题和证据，由原作者修订，避免同时修改同一报告

3. 执行阶段

按以下顺序开展：

阶段 1：统一摸底
由统筹者先建立框架调用路径、初步能力清单、保真标准、公共术语和报告模板，
写入共享材料后再分派领域分析任务。

阶段 2：分批并行分析
领域 agent 基于统一材料分析各自对象的接口、状态模型、实现路线和保真缺口，
包括 LLM 仿真可行性。每批完成后，由统筹者检查覆盖情况并安排下一批。

阶段 3：共享发现合并与公共设计
统筹者在各批次之间复核并合并公共发现，汇总可以共享的基础设施，例如：
状态存储、身份空间、ID、虚拟时间、对象存储、
错误表示、快照、隔离和调用记录。

对 LLM 仿真路线，进一步分析状态检索、结构化输出、
变更校验、模型调用、缓存和回放机制的共享可能性。

只复用已确认的公共机制。
不要强行把不同服务的业务语义统一成同一种 CRUD 模型。

共享设计更新后，统筹者通知受影响的领域 agent 检查并修订报告。
公共材料是协作依据，但领域 agent 仍需核实与自身结论相关的源码证据。

阶段 4：交叉复核
初稿完成后安排非原作者复核，检查共享资源、跨入口状态、跨服务任务及设计冲突。
由原作者修订，统筹者确认审查问题已处理或明确标为待确认。
在相应报告中记录主要审查问题、证据和处理结果。

阶段 5：验证与实施规划
统筹者综合经复核的报告，确定总体架构、代表性试点、验证门槛和后续实施批次。

4. 共享知识要求

公共结论必须注明证据、适用范围和验证状态。
事实、设计建议、假设与待确认问题分开记录。
不要仅依赖 agent 间的聊天传递共享知识；经复核的公共结论必须写入共享文件。
避免多人同时修改同一共享文件，也不要在证据冲突尚未解决时将其写成确定结论。

十、验证计划

本阶段设计验证，不执行真实服务写入。

验证计划至少包含：

- 工具 schema 和输出结构检查
- 参数边界与错误行为验证
- 状态转换与业务不变量验证
- 多工具组合和不同操作顺序验证
- 多入口状态一致性验证
- 并发、隔离、重置和复现验证
- 多样环境与新任务结构验证
- 数据质量和已知模拟偏差检查
- LLM 仿真的状态漂移、幻觉、错误接受和答案泄露检查
- 不同实现路线的保真、吞吐、延迟和成本比较

设计后续与真实服务进行差分验证的方法，
区分可用现成记录验证的部分与需要受控真实环境的部分。
说明动态 ID、时间戳等非确定字段如何比较。

真实服务写入验证仅提出方案和所需条件，不在本阶段执行。

十二、最终决策输出

最终回答：

1. 各对象可以达到怎样的保真程度，主要难点是什么？
2. 哪些能力必须优先实现，才能生成有迁移价值的轨迹？
3. 哪些近似会明显损害数据质量？
4. 哪些组件可以共享，哪些必须独立实现？
5. 如何支持超出现有任务的新任务和新调用组合？
6. 如何证明模拟环境具有可信的行为一致性？
7. 如何扩展到大规模并发合成，并保持隔离和可复现？
8. 各对象应采用代码、LLM 主导还是混合实现，依据是什么？
9. LLM 仿真如何保障状态一致性、控制偏差，并降低总成本？
10. 第一批应实现哪些对象及能力，为什么？

优先级综合考虑：
行为保真、任务多样性、共享收益、开发与运行成本、
验证可行性和数据质量风险。

当前 finalpool 覆盖率只作为辅助指标。

提出一个有代表性的首轮试点，
验证工具契约、状态变化、错误恢复和独立结果评测，
并列出后续扩大覆盖范围的验收门槛。

同时说明该试点能否比较代码与 LLM 仿真的价值；
如果不能，补充一个范围明确的 LLM 仿真对照试点。

完成分析和交叉复核后结束本阶段，
不要自动进入实现。
