# t8n-analyze

分析用户给定 dump，产出正式通过率、未通过任务的三类归因和可审阅的重跑候选。分类描述这一次运行的证据，不把单次失败等同于模型永久不具备该能力。

## 确定范围

- 使用用户指定 checkout，否则使用当前 Toolathlon 仓库。确认存在 `scripts/calculate_pass_rate.py`，先核对其当前接口和统计逻辑；所有仓库相对路径从仓库根目录解析。
- 明确 dump 绝对路径、任务目录层级和可选任务清单。标准布局是 `<dump>/finalpool/<task>/`；直接给定任务集合目录时使用 `--tasks-folder .`。不要猜测不存在的 dump，也不要默认将整个 `results/` 当成一次实验。
- 用户指定任务清单时以它为准。未指定时检查 `<dump>/.t8n-run/` 的启动记录：只有能确定为目标实验完整清单时才采用该清单，不直接使用最近一次子集补跑的清单。无法确定原始全集时按现有任务目录统计，明确“分母仅为已有任务目录，无法包含从未创建目录的任务”。记录清单来源和范围限制。
- 对多次原地补跑的 dump，本次默认分析每个任务的当前产物；旧 `legacy_results` 只在解释历史变化时单独引用，不能混入本次分子、分母或冒充当前证据。记录可确认的模型、参数和运行批次；身份不明或新旧配置混合时说明限制。
- 如果实验还在写入，标注采样时间和“运行中快照”。`status.json` 的残留 `running` 不足以证明进程存活；必要时只读核对对应进程和容器。仍在运行的任务不作终局归因，也不列为立即重跑对象。

## 用现有脚本计算通过率

从仓库根目录运行，按实际范围传入可选参数，不另写一套通过率算法：

```bash
python3 scripts/calculate_pass_rate.py "$dump_path"
python3 scripts/calculate_pass_rate.py "$dump_path" --task-list "$task_list" --tasks-folder "$tasks_folder"
```

上面是两种调用形式，选择适用的一种。保存实际命令、stdout / stderr 和退出状态；命令失败先解决路径或输入问题，不从错误输出拼出统计结果。

当前口径如下；以后脚本变动时以当前源码为准并说明变化：

- 只读当前任务叶子的 `eval_res.json`，仅 JSON 布尔 `pass=true` 为通过；正式通过率为 `passed / total_tasks`，不能剔除环境失败后替换这个指标。
- 保留脚本的五种结果状态：`passed`、`failed`（`pass=false`）、`no_eval`（文件缺失或 `pass=null`）、`missing`（任务目录缺失）、`invalid`（JSON 或字段无效、读取失败）。后四种共同组成“未通过”，不能全部写成评分失败。
- 显式任务清单会忽略空行、整行注释并去重；缺失目录的任务仍计入分母。省略清单时不继承环境变量 `TASK_LIST`。任务集合为空时通过率是 N/A，不是 0%。
- 不用 `status.json`、根层 `eval_stats.json`、递归聚合文件或日志中的 `SUCCESS` 替代正式 pass 判定。
- 生成结构化清单时可导入同一脚本的 `calculate_pass_rate()` 复用返回字典，不复制统计逻辑。运行中的产物可能变化，两次读取不一致时报告差异，不能把不同时间的数字拼成一份一致快照。

## 对每个未通过任务建立证据链

所有 `failed / no_eval / missing / invalid` 任务均需有分析行；先确认运行阶段，再分类。

1. 读取当前 `eval_res.json` 中的 `failure` / `details` 和 `status.json`，确定预处理、Agent、评估各阶段的状态。`pass=false` 本身不能证明模型错误，`pass=null` 也不能证明环境错误。
2. 查阅该任务的 `run.log`、`container.log`、`traj_log.json`；需要时读取 `conversation_history/` 和任务工作目录中的相关产物。先用 `rg` 定位失败、恢复、最终输出，再读上下文；关键词命中不能直接决定分类。
3. 对照 `tasks/<TASKS_FOLDER>/<task>/` 中的任务要求、配置和 `evaluation/main.py` 及其相关检查，解释“要求什么、实际做了什么、哪里不满足”。直接给定任务集合目录时，任务定义的 `TASKS_FOLDER` 需另外从启动配置或仓库确认，不能用统计参数 `.` 代替。
4. 环境故障要定位到实际边界：宿主机/调度器、任务容器、预处理数据、本地依赖服务、MCP、远端服务、模型 API、评估器。必要时只读追查实现；当前服务恢复不代表运行当时可用。
5. 写出时间顺序：故障或错误决策 → 后续尝试 → 恢复/仍阻塞的证据 → 最终未通过原因。每个归因引用文件相对路径及行号、JSON 字段或工具调用 ID，附最短必要摘录；不在报告复制认证值。

任务缺失、日志不足、运行未完成、混合因素无法判清时，保留事实与待补证据，不强行归类。分析期只读取已有实验和任务代码，新增分析报告；不执行任务脚本、评估器、部署或远端探测来“验证”，这些可能改写本地或远端状态。

## 三类归因

结果状态与原因分类是两列，不能混用。只对证据足够的未通过任务填入类别 `1 / 2 / 3`：

| 类别 | 定义与所需证据 | 下一步倾向 |
| --- | --- | --- |
| 1：模型能力失败 | 关键依赖可用，未发现足以影响结论的环境干扰；轨迹和检查结果能定位到理解、规划、计算、工具使用、输出或验证错误。这里的“纯模型”仅限本次证据范围。 | 改进模型、提示或策略后做对照；若要测随机性，单独说明同配置重复运行的目的。 |
| 2：环境阻塞 | 存在具体环境、MCP、服务、模型 API 或评估基础设施故障，阻断完成任务或可靠评分的必要步骤，且运行结束前未被有效恢复或绕过。允许同时存在次要模型错误，但应分别记录。 | 先修复明确依赖，再重跑受影响阶段；只有评估器故障时优先检查能否仅重评。 |
| 3：环境干扰已绕过，最终仍未通过 | 发生了影响任务的环境问题，模型通过替代工具、路径或方法获得了满足相关要求的数据/状态；后续证据证明原阻塞已解除，但任务因剩余错误仍未通过。必须分别解释绕过和最终失败。 | 同时查看剩余模型问题与环境消耗；必要时在健康环境下对照重跑，判断绕过成本是否影响表现。 |

分类边界：

- 第 3 类的“绕过”要有后续工具返回、产物或状态证明，且满足任务约束。模型说“我已解决”、忽略失败步骤、伪造数据、改用不能满足要求的数据、修改评分条件都不算有效绕过。
- 普通可恢复警告、探索时的无效参数、错误路径/ID 或模型误用工具，不因返回了错误就成为环境干扰。核对有效调用和上下文；只有确实影响任务的环境故障才进入第 2/3 类。
- 有关键环境阻塞尚未解除时归第 2 类，即使其他故障已被绕过。障碍全部解除后仍失败，且剩余失败可解释时归第 3 类；若只能证明绕过、不能判清最终失败，保留绕过事实并标记待判定。
- 超时、超轮数、输出缺失是现象。区分模型反复错误消耗预算、服务阻塞消耗预算、绕过环境后预算不足；无法区分时待判定，不能按终止状态机械分类。
- 评估连接失败、评估器依赖缺失或有代码证据的评估缺陷归第 2 类，阶段标为评估；任务产物确实不满足正确检查属于模型侧证据。仅怀疑评分或 ground truth 有问题时标待判定。
- 额外设置 `analysis_status` 为 `已归类 / 待判定 / 运行中 / 未开始`；后三者的 `category` 留空。这是分析状态，不增加第四种原因类别。缺失目录不能直接归模型或环境；只有证据证明尚未开始时才标“未开始”。
- `pass=true` 只参与通过率统计，本次不逐项做失败归因。因此第 3 类数量不代表所有成功绕过环境的任务数。

## 保存报告与重跑建议

默认输出到 `<dump>/.t8n-analyze/<UTC时间>-<唯一后缀>/`，也可使用用户指定位置。目录每次新建，放在任务集合目录外，不覆盖实验叶子文件、旧报告或原有统计。若输入直接是任务集合目录，默认以其父目录为 dump 根；布局无法确认时选择明确在集合之外的输出位置并报告。

保存以下产物：

| 文件 | 内容 |
| --- | --- |
| `pass-rate.txt` | 原脚本的完整输出及错误信息；在报告中记录对应命令和退出状态。 |
| `task-list.txt` | 本次实际纳入分母的完整任务名集合，一行一个，包含缺失目录的任务；记录其来源，便于复核。 |
| `task-analysis.csv` | 每个未通过任务一行，可编辑；列见下文。使用 CSV writer 正确处理逗号、引号和换行。 |
| `report.md` | dump、分析时间、配置与范围、正式通过率及五种状态数量、三类及待判定/运行中/未开始数量；逐任务结论与证据、共同环境问题、按优先级排列的修复和重跑建议。 |
| `rerun-candidates.txt` | 建议再次执行 Agent 的任务 basename，一行一个、去重。仅作为候选，逐项前置条件在 CSV 和报告说明；无候选则保存空文件并说明。 |

CSV 列使用：

```text
task,result_state,analysis_status,category,confidence,failure_stage,environment_issue,bypass_evidence,final_failure,evidence,next_action,prerequisite,in_place_behavior
```

- `confidence` 用 `高 / 中 / 低`，反映证据强度；未归类行写明缺失的证据。`environment_issue` 写具体服务和错误，`bypass_evidence` 指向后续成功证据，`final_failure` 写最终未通过原因，不能只复述类别名。
- `next_action` 区分修环境后重跑、健康环境对照、模型改进后重跑、仅重评候选、补跑未开始任务、补证据、等待运行完成。重评是否可行要结合评估所需远端状态/产物是否保留；它不自动包含再次执行 Agent。
- 候选清单仅收录已给出具体再次执行 Agent 建议的任务，包括有明确范围证据的未开始任务；不自动把全部第 2 类纳入。仅重评、证据不足、仍运行的任务不进入该清单。
- `in_place_behavior` 按当前 `run_parallel.py` 的 `filter_tasks_with_existing_results` 检查，填 `执行 / 跳过 / 待核对`。该规则与 pass 不同：当前预处理完成且 `running=done`、`evaluation` 非 null 的任务会跳过，评分失败也一样；预处理完成后的 timeout / max_turn_exceeded 也跳过。还需检查源码中的缺失/无效状态回退，不能仅凭 `pass=false` 决定。
- 对会被原地入口跳过的候选，明确建议使用新的 dump 做独立重跑，或另行确定强制重跑方案；当前入口没有 force 开关。不能把生成候选清单说成能够直接完成原地重跑，也不修改状态文件绕过过滤。
- 本技能到分析产物和建议为止。用户后续授权启动时，交给仓库 [t8n-run](../t8n-run/SKILL.md) 审阅具体任务、参数与部署；其中含 Notion 的作业仍要求整体串行且避免跨作业重叠。

交付前核对：五种结果数量之和等于分母；CSV 任务集合恰好等于四种未通过状态的并集且无重复；三类已归类数加其余分析状态数等于未通过数；候选是上述任务的无重复子集且符合行动建议。已归类行须有可定位证据，运行中或无法解释的任务不能包装为确定的终局归因。

## 聊天回复

最终回复先给出正式通过率（通过数 / 分母）、三类及待判定/运行中/未开始数量，然后直接展示三张独立的 Markdown 任务表：

1. **第 1 类：模型能力失败（N 个）**：列为 `任务 | 结果状态 | 失败原因与关键证据 | 下一步建议`。
2. **第 2 类：环境阻塞（N 个）**：列为 `任务 | 结果状态 | 阻塞问题与关键证据 | 下一步建议`。
3. **第 3 类：环境干扰已绕过，最终仍未通过（N 个）**：列为 `任务 | 结果状态 | 环境问题及绕过证据 | 最终失败原因 | 下一步建议`。

每张表完整列出该类全部任务，一任务一行，与 CSV 分类一致；不能只展示数量、示例任务或报告链接。某类为空时仍保留对应表，使用“无（0 个）”占位行，其他列填 `—`，该行不计作任务。表内证据用简短说明和可定位链接，详细轨迹留在报告；重跑建议涉及原地跳过时在建议列说明。

待判定、运行中、未开始的任务另用简短列表说明任务名和状态原因，不塞进三类表。最后给出优先处理的共性问题、报告/CSV/候选清单路径及后续执行状态。
